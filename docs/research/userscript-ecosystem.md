# Modern Userscript Ecosystem: Managers, APIs, and Distribution (2025–2026)

- **Date:** 2026-11-21
- **Tracking Issue:** `#3`
- **Scope:** Active userscript managers under Manifest V3, modern `GM.*` APIs and metadata directives, security/bundling constraints, and distribution/auto-update channels — evaluated to inform Iteration 1 of **Pikabu Expand Comments**.

## Executive Summary

1. **Manifest V3 stabilized around browser-native `userScripts` APIs.** Both Tampermonkey and Violentmonkey ship Manifest V3 (MV3) builds on the Chrome Web Store, while Firefox continues to support MV2 alongside its MV3 `browser.userScripts` API (desktop Firefox 136+, Firefox for Android 138+). On Chrome 138+, the global **Developer Mode** requirement was replaced by a per-extension **Allow User Scripts** toggle.
2. **Target `GM.*` async APIs, `@match`, `@noframes`, and an isolated DOM context.** Using `GM.getValue` / `GM.setValue` and `GM.registerMenuCommand` maximizes cross-manager compatibility. Avoid `innerHTML` (Trusted Types) and bundle TypeScript/ESM source into a single **non-minified, readable classic IIFE** `.user.js` file — required both by browser userscript execution contexts and by GreasyFork's strict no-minification policy.
3. **Separate click-to-install hosting from GitHub Release attachments.** GitHub Releases (`releases/latest/download/...`) serve assets via `objects.githubusercontent.com` with `Content-Disposition: attachment`, which frequently causes browsers to save `.user.js` to disk instead of triggering manager install prompts. Prefer **GitHub Pages** or **`raw.githubusercontent.com`** (5-minute Fastly cache) for direct GitHub installs/updates, and **GreasyFork** (synced via GitHub webhooks, without overriding `@downloadURL`) for public discovery.

## 1. Active Userscript Managers & Manifest V3 Reality (2025–2026)

### 1.1 Browser Platform Baseline

#### Chromium (`chrome.userScripts` & Chrome 138)

Chrome's MV3 [`chrome.userScripts`](https://developer.chrome.com/docs/extensions/reference/api/userScripts) API allows extensions to register and execute user-provided scripts in either an isolated `USER_SCRIPT` world (default) or the page's `MAIN` world, with configurable per-world CSP and messaging via `chrome.userScripts.configureWorld({ csp, messaging })` (messaging defaults to `false`).

- **Pre-Chrome 138:** Running MV3 `chrome.userScripts` required users to turn on the global **Developer Mode** switch on `chrome://extensions`, which exposed developer features globally and conflicted with enterprise policies ([Chrome for Developers Blog](https://developer.chrome.com/blog/chrome-userscript)).
- **Chrome 138+:** Google replaced the global Developer Mode requirement with a granular, per-extension **Allow User Scripts** toggle on each extension's Details page (`chrome://extensions/?id=<extension_id>`), improving security and enabling enterprise adoption ([Chrome for Developers Blog](https://developer.chrome.com/blog/chrome-userscript); [Tampermonkey FAQ Q209](https://www.tampermonkey.net/faq.php#Q209)). Older Chromium builds (< 138) still require global Developer Mode.

#### Firefox (`browser.userScripts` & MV2 Coexistence)

Firefox implemented MV3 support starting in Firefox 109 while maintaining MV2 compatibility. For MV3 userscript managers, Mozilla added the [`browser.userScripts`](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/userScripts) API (requiring `userScripts` under `optional_permissions`, requested dynamically via `browser.permissions`, plus matching `host_permissions`):

- Supports `register()`, `update()`, `unregister()`, `getScripts()`, `configureWorld()`, `getWorldConfigurations()`, and `execute()`, targeting either `USER_SCRIPT` or `MAIN` worlds ([MDN `userScripts` API](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/userScripts)).
- Desktop Firefox rollout started around Firefox 136, **Firefox for Android** support landed around Firefox 138+, and `userScripts.execute()` reached support in Firefox 153 ([MDN `userScripts` API](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/userScripts); [FireMonkey](https://github.com/erosman/firemonkey)).

### 1.3 Practical Platform Takeaways

- **Desktop Chrome / Edge:** **Tampermonkey** and **Violentmonkey** both work reliably on MV3 once the user enables Chrome 138+'s per-extension **Allow User Scripts** toggle. Our README installation instructions should explicitly document that one-time toggle so Chrome users are not confused when a freshly installed script fails to run.
- **Desktop Firefox:** **Violentmonkey** (MV2), **Tampermonkey**, and **FireMonkey** all work reliably without the Chrome toggle hurdle. **Greasemonkey 4** still receives occasional maintenance releases (4.14 in June 2026), but its reduced API surface makes it a secondary target compared to Violentmonkey, Tampermonkey, and FireMonkey.
- **Mobile Browsers:**
  - **Android:** **Firefox for Android** (with Violentmonkey, Tampermonkey, or experimental FireMonkey) and **Microsoft Edge for Android** (with Tampermonkey) are the mainstream, non-niche paths. Note that Pikabu Expand Comments targets desktop **Post Pages** per [GLOSSARY.md](../../GLOSSARY.md), so mobile is out of scope for Iteration 1 unless users request desktop-mode mobile support later.
  - **iOS / Safari:** **Userscripts** (`quoid/userscripts`, free/open-source) and **Tampermonkey for Safari** are the viable options.

### 2.3 CSP & Trusted Types Considerations

- **Execution World Isolation vs. Page CSP:** Under MV3 `chrome.userScripts`, scripts in the `USER_SCRIPT` world run under the world's own CSP (configured via `chrome.userScripts.configureWorld()`), whereas scripts injected into `MAIN` world share the host page's JS context and CSP ([Chrome `userScripts` API](https://developer.chrome.com/docs/extensions/reference/api/userScripts)). Declaring `@sandbox dom` (Tampermonkey) and `@inject-into content` (Violentmonkey / Userscripts) keeps a DOM-only userscript out of the host page's JS world and avoids page-script collisions.
- **Trusted Types (`require-trusted-types-for 'script'`):** On sites enforcing Trusted Types, assigning raw strings to HTML/script sinks (`innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`) throws a `TypeError` unless wrapped in a `TrustedHTML` policy ([MDN Trusted Types](https://developer.mozilla.org/en-US/docs/Web/API/Trusted_Types_API)).
  - **Best practice:** Build UI nodes purely with `document.createElement()`, `textContent` (not a Trusted Types sink), `setAttribute()`, and `append()` — never `innerHTML`.
- **Styling under strict `style-src` CSP:** Inline `<style>` tags can be blocked by strict `style-src` policies lacking `'unsafe-inline'`. Constructed stylesheets (`new CSSStyleSheet()`, `.replaceSync(css)`, attached via `document.adoptedStyleSheets` or `shadowRoot.adoptedStyleSheets`) are **not governed by `style-src`** ([MDN `Document.adoptedStyleSheets`](https://developer.mozilla.org/en-US/docs/Web/API/Document/adoptedStyleSheets)). `GM.addStyle` also appends a `<style>` element to `<head>` (with Tampermonkey offering CSP header modification settings), though it cannot style inside a Shadow DOM (`GM_addElement` or `shadowRoot.adoptedStyleSheets` is needed there).

### 2.4 ESM & Bundling Implications

- **No native multi-file ESM in userscripts:** Browser `userScripts` runtimes and script managers evaluate classic scripts wrapped in a manager-provided closure (passing `GM`, `GM_info`, etc.), not ES module graphs. Native `import`/`export` statements fail directly inside raw userscripts ([Violentmonkey Docs](https://violentmonkey.github.io/api/metadata-block/)).
- **Top-level `await` is NOT portable:** Violentmonkey added `// @top-level-await` in v2.19.2 (incompatible with `@unwrap`), but it is a Violentmonkey-specific directive. Wrapping the bundle entry in an async IIFE (`(async () => { ... })();`) works identically in every manager.
- **Recommended toolchain output:** Author modular TypeScript/ESM in `src/`, then bundle into a single classic **IIFE** (`format: 'iife'`) `.user.js` artifact with the `// ==UserScript==` banner prepended cleanly at byte 0.
  - **Do NOT minify** the published `.user.js` if distributing on GreasyFork (and keeping it readable aids user auditability everywhere).
  - External libraries, if ever needed, must either be bundled cleanly (within GreasyFork's 2 MB cap) or loaded via `@require` from approved CDNs / with Subresource Integrity (SRI) hashes ([GreasyFork External Scripts Policy](https://greasyfork.org/en/help/external-scripts)). For a focused DOM utility like Pikabu Expand Comments, **zero runtime dependencies** is ideal.

## 3. Distribution & Auto-Update Channels

### 3.1 Auto-Update Mechanics & Version Rules

Userscript managers check for updates periodically and on demand using three metadata fields ([Tampermonkey Docs](https://www.tampermonkey.net/documentation.php#meta:updateURL); [Violentmonkey Metadata](https://violentmonkey.github.io/api/metadata-block/); [FireMonkey Docs](https://erosman.github.io/firemonkey/)):

- **`@version`**: Required for updates. Must strictly increase on every release. Tampermonkey compares dot/dash-separated numeric and pre-release tokens sequentially (e.g., `1 == 1.0 == 1.0.0`, `16.4 == 16.04`, `1.10.0-alpha < 1.10.0`, `Alpha-v1 < Alpha-v2 < Alpha-v10 < Beta`, plus SemVer and `YYYY-MM-DD`). Sticking to standard SemVer (`MAJOR.MINOR.PATCH`) works uniformly across all managers and GreasyFork.
- **`@updateURL`**: Points to either a lightweight metadata-only `.meta.js` file (just the `// ==UserScript== ... // ==/UserScript==` block) or the full `.user.js` file. Managers fetch this first and compare `@version`.
- **`@downloadURL`**: Points to the full `.user.js` bundle downloaded once `@updateURL` reports a higher `@version`. If omitted, managers fall back to `@updateURL` or the original install URL.

### 3.3 Avoiding Channel Conflicts Between GitHub and GreasyFork

A common pitfall when publishing to both GitHub and GreasyFork is embedding GitHub `@updateURL` / `@downloadURL` directives in the same file synced to GreasyFork:

- GreasyFork prohibits pointing users to alternate external download sources ([GreasyFork Code Rules](https://greasyfork.org/en/help/code-rules)) and generates its own `update.greasyfork.org` update URLs automatically.
- **Clean pattern:**
  - If **GreasyFork** is the primary distribution channel (synced via GitHub webhook from a built readable `.user.js` on a release/dist branch or GitHub Pages URL), **omit** `@updateURL` and `@downloadURL` from the GreasyFork-synced artifact so GreasyFork injects its own canonical URLs cleanly.
  - If **GitHub Pages** (or a `dist` branch on `raw.githubusercontent.com`) is used for direct non-GreasyFork installs, emit `@updateURL` (pointing to `.meta.js`) and `@downloadURL` (pointing to `.user.js`) on that build target (or keep GitHub Pages as the sole self-hosted channel in Iteration 1 and add GreasyFork webhook sync when ready for public listing).

## 4. Concrete Implications & Recommendations for Iteration 1

Applying these findings to **Pikabu Expand Comments** (using the domain language in [GLOSSARY.md](../../GLOSSARY.md)):

1. **Manager Support Tiers**
   - **Tier 1 (Primary, tested):** Tampermonkey (Chrome/Edge MV3, Firefox) and Violentmonkey (Chrome/Edge MV3, Firefox MV2).
   - **Tier 2 (Compatible by design):** FireMonkey (Firefox desktop) and Safari Userscripts (`quoid/userscripts`), by sticking to standard `GM.*` storage and avoiding manager-specific APIs.
   - **Out of scope for Iteration 1:** Mobile browsers (Post Pages are desktop Pikabu.ru pages) and Greasemonkey 4-only workarounds (though avoiding `GM.addValueChangeListener` and keeping a tiny CSS fallback means GM4 mostly works for free).

2. **Recommended Metadata Block Strategy**
   - Use **`@match`** (not `@include`) scoped narrowly to Pikabu desktop **Post Pages** (exact URL pattern to be finalized by the Pikabu DOM/routing research).
   - Always include **`@noframes`** so the script never runs inside embedded iframes.
   - Use **`@run-at document-end`** (or `document-idle`) since an **Expansion Run** interacts with rendered Comment Batch and Reply Branch loaders rather than intercepting pre-DOM requests.
   - Declare **`@grant`** explicitly with the minimal async surface needed:
     - `// @grant GM.getValue` and `// @grant GM.setValue` — to persist the **Auto-Expand on Visit** user preference.
     - `// @grant GM.registerMenuCommand` — to expose a manual **Expansion Run** trigger / **Auto-Expand on Visit** toggle in the manager popup menu (guard with `typeof GM?.registerMenuCommand === 'function'` for Safari Userscripts resilience).
     - `// @grant GM.addStyle` — only if we inject minimal UI styles (otherwise prefer constructed `CSSStyleSheet` / `document.adoptedStyleSheets` or a tiny `<style>` helper using `textContent` so styles work even without `GM.addStyle` and under strict `style-src` CSP).
   - If Iteration 1 interacts purely with the DOM (clicking loaders / observing DOM mutations without reading page JS globals), include both `// @sandbox dom` (Tampermonkey) and `// @inject-into content` (Violentmonkey / Userscripts) for maximum isolation and CSP resilience. _(If Pikabu's Comment Batch or Reply Branch loading requires calling page-level JS internals, revisit this to `raw`/`page`.)_

3. **Build & Code Hygiene**
   - Write modular TypeScript/ESM in `src/` with zero runtime dependencies.
   - Bundle to a single **non-minified, human-readable classic IIFE** (`dist/pikabu-expand-comments.user.js`) with preserved comments/identifiers and a SemVer `@version` matching `package.json`. Never rely on Violentmonkey's `@top-level-await`; use a standard async IIFE.
   - Build any injected UI strictly with `document.createElement()` + `textContent` (zero `innerHTML`) for Trusted Types compliance.

4. **Distribution & Onboarding**
   - **Direct GitHub channel:** Publish the readable `.user.js` (and `.meta.js`) via **GitHub Pages** (via GitHub Actions on release) or a dedicated `dist` branch served via `raw.githubusercontent.com` — **not** GitHub Releases attachment links for human 1-click installation (due to `Content-Disposition: attachment`).
   - **Public discovery channel (optional in Iteration 1, easy to add at any time):** Publish to **GreasyFork** synced from GitHub via webhook, omitting external `@updateURL`/`@downloadURL` on the GreasyFork artifact so GreasyFork manages updates cleanly and our readable non-minified bundle passes GreasyFork's code rules out of the box.
   - **README onboarding note:** Explicitly instruct Chrome 138+ users to enable **Allow User Scripts** on the Tampermonkey/Violentmonkey Details page in `chrome://extensions` (and **Developer Mode** on Chromium < 138).

5. **Newly Surfaced Fog / Open Questions**
   - **Does Pikabu.ru require `MAIN` / `page` world access or is `dom` / `content` isolated world sufficient?** (Depends on whether Comment Batch and Reply Branch loaders can be triggered purely via DOM clicks/events vs. Pikabu's internal JS APIs; to be answered by Pikabu DOM/architecture research.)
   - **Does Pikabu.ru enforce strict CSP or Trusted Types headers?** (If we stick to `document.createElement` + `textContent` + `adoptedStyleSheets`/`GM.addStyle` and isolated world, we are resilient either way, but verifying Pikabu's live headers is still worthwhile.)
   - **Exact bundler choice for Iteration 1** (e.g., esbuild, Rollup, Vite + `vite-plugin-monkey`, or tsdown/rolldown) to emit a clean non-minified IIFE with metadata banner and live dev reload — should be evaluated in the build/tooling setup ticket.
